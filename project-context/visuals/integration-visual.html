One turn, end to end

The browser validates, then the server validates the same rules again — a client-side rule is a convenience and never a control. From there the route does everything that must happen either way, hands the turn to whichever engine CHAT_ENGINE selects, and pumps frames back until done.

What the customer sees, and what the operator sees

Two frames in the union are operator-only. clientFlags.trace gates them server-side, so the crew stays invisible on the customer path — the wire-level expression of “one assistant, not a crew”. Case 5 and case 6 are the same question asked with the flag on and off.

When it goes wrong

Four failure paths, each with a defined shape. The distinction that took a bug to learn: a customer closing the tab is a normal end to a turn, not a fault.

  1. malformed bodyHTTP 400, JSON — not SSE. A request that never became a turn does not get a turn's envelope.
  2. mid-turn failureIn-band error frame, then done. The stream stays well-formed all the way to the terminal frame.
  3. client disconnectcancel() aborts server-side. Case 9 observed a prompt_trace and nothing else: no tool calls, no ticket stub, no spend.
  4. turn timeoutAbortController at 120s. An explicit budget, never an SDK default.

send() is total — it never throws. A dead stream drops frames instead of raising, because a throw from inside engine code unwinds into the engine's own catch and gets logged as a turn failure. That was the ERR_INVALID_STATE class of bug in the 2026-08-23 traces: turns that had already succeeded, recorded as failures.

What the run found

This persona records findings; it does not fix them — writing to another persona's files would breach the AAMAD agent contract. Three were handed to their owners and closed the same day.

INT-01The default engine never escalatedclosed · same day

“I want a refund” on the keyless demo path returned the order summary and resolved — no escalation frame, no ticket. The reply text was honest, so this was a capability gap rather than a false statement, but on the default engine a customer asking for a refund was never routed to a person. ADR-16 ruled escalation a TurnEngine obligation: engines may differ in how they decide, not in whether they route. A money-vocabulary matcher now opens the stub in code. Re-verified live, and “why was my order cancelled” still resolves rather than over-escalating.

INT-02Today was derived from UTC, not the server's dayclosed · same day

Observed at 21:29 CDT: asOf=2026-08-28. West of UTC, an order placed today reads as yesterday, every evening. The fix split the two concerns — toIsoDate stays UTC because the shift arithmetic is anchored on UTC-midnight dates; a new todayIsoLocal() feeds resolveAsOf only. The first attempt made toIsoDate local outright, which would have moved every shifted order date back a day west of Greenwich — a cosmetic off-by-one turned into a data defect, caught by asking which callers depended on the UTC anchoring.

TRACEAn external call the architecture didn't recordclosed · same day

server/data/holidays.ts cited a SAD amendment that did not exist, while the SAD still listed only the Anthropic API and the DuckDB file. The codebase was calling a third party the architecture had never admitted. ADR-15 now records the Nager.Date dependency as optional — degrades, with its safety properties and the reason carrier tracking was rejected in its place.

DEF-04A clarifying question renders as a finished turnopen · @qa.eng

On the sdk path, order 999999999 returns done:resolved while the reply asks the customer to double-check the number. lib/status.ts maps resolved to the green done tone with “Answered from order data.” The UI is faithfully reporting what the server sent — the divergence is upstream of the client. Confirmed on two models, so it is not model-specific.

One adapter requirement is only partially met. EscalationPackage is validated at the boundary; StreamEvent is not. parseFrame accepts any object with a type field and casts, so a malformed frame would reach the FSM as an unknown variant. Zod is already a dependency. Open, with the client-side test gap — lib/fsm.ts and lib/status.ts are pure, trivially testable, and untested.
