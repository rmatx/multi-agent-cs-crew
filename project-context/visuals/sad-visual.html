Scope

The PRD freezes this explicitly: build P0; schedule P1 only if time allows; P2 and OUT are forbidden without revising the document. Each P0 feature traces to a market problem in the MRD, so nothing below was invented at architecture time.

Two boundaries that blur in conversation

support_tickets exists in the database but is out of the MVP tool surface — only its category enum is used, and only in code. And returns are advisory: the agent explains eligibility and executes nothing. That second boundary is enforced by the tool registry, not by prompt wording, which is why it can be tested by counting registered tools.

Layer 01 — the request

One message, one process, one stream back

ADR-09 collapses UI and API into a single Next.js App Router app, so the whole path below runs in one Node process. The response is a single SSE envelope carrying tokens, hop events, citations and the terminal status.

Layer 02 — orchestration

A hop is an agent transfer, not a tool call

This is the rule the backend has to implement exactly, and the one most easily mis-read. Four agent transfers are the entire budget for a turn; the tool calls inside a transfer are free, however many there are.

Least privilege

The allowlist is the safety boundary

Eight tools exist in the process. Seven are pure reads; one writes, and only the escalation agent can reach it. Nothing that moves money is registered at all, so "the agent refused to refund" is a property of the tool registry rather than of a prompt.

Not registered in the MVP process

Payments, refunds, order cancellation, membership mutation, shell, and arbitrary network tools. No built-in Bash, Write, WebFetch or WebSearch either. A turn that needs any of them can only escalate — that is the whole design, and NFR-SAFE-01 is checked by counting registered tools, not by reading transcripts.

Layer 03 — time

A frozen 2024 catalog, demoed against a moving clock

The practice database stops at 2025-01-01 and cannot be written to, yet the demo has to show a live 14-day return window and an active Plus trial. The shift happens inside the repository adapter, so raw dates never reach an agent prompt.

Why evals must pin the clock

With asOf defaulting to today, shiftDays grows by one every day, so any expectation written against an absolute date rots silently. Every eval that touches a return window or an active trial sets AS_OF_DATE, pins DATE_SHIFT_DAYS, or uses an overlay persona.

Layer 04 — budgets

Three ways a turn ends; one of them leaves no trace on the customer's record

Budgets only mean something as transitions. Answered and Escalated are both legitimate successes — containment is a target, not a mandate. Aborted is the only exit that writes no ticket stub.

What makes an escalation package complete

conversationId, intent, urgency, transcript_summary, reason_code and suggested_category are non-empty; entities, tools_tried and citations are present but may be empty; reason_code is one of the seven allowed values. entities must carry an order or user id unless the reason is customer_requested_human or ungrounded — where the customer may never have given one.

Build sequence

Depth first — one grounded turn before six agents

The order below is load-bearing: each step is only started once the previous one is green, because the risky parts of this system are the contract seam and the temporal layer, not the agent count.

  1. 01Freeze the DTO packageChatRequest, StreamEvent, EscalationPackage, ReasonCode — written at the end of Setup, before the frontend builds against a mock. The mock imports these types; it never restates them.
  2. 02Sprint 1 vertical slice: one WISMO turnorderId → POST /api/chat → triage → order-specialist → get_order through the overlay and shift → streamed grounded status → done{resolved}. Exit: TTFT under 5s, hops = 1, zero money tools registered, trace shows asOf / shiftDays / overlayHit.
  3. 03Eval runner, alongside the sliceTwo scripts at minimum: WISMO grounded with a pinned clock, and refund → escalate asserting a schema-valid package and zero money tool calls. Not deferred to QA.
  4. 04Escalation + ticket stub + payment routeProves the safety boundary is real rather than documented.
  5. 05faq-policy + search_policy at 0.55Proves grounding and escalate-over-invent.
  6. 06returns-advisor reusing order toolsProves the hop accounting rule under a chained case.
  7. 07plus-specialist + membership overlayProves the temporal layer under a second read path.
  8. 08SQLite stores, CSAT, trace panelDemo polish — deliberately last.

Resolved 2026-08-13 · SAD-OQ-6 — scope the CI fixture by table, not by row

The practice database is 151 MB, over GitHub's 100 MB hard limit, so ADR-12's "repo fixture copy" was not executable as written. Nearly all that weight is events (6.5M rows) and sessions (1.4M) — tables the MVP never reads. Copying only the five MVP-read tables, with every row intact, yields novamart_ci.duckdb at 3.2 MB: under even GitHub's 50 MB soft warning, and verified row-for-row against the full database.

Row-subsetting to demo personas turned out to be unnecessary. Whole tables keep the fixture a sample-free replica, so the temporal measurements above reproduce in CI unchanged, and the generator needs no persona input — which matters, because demo_overlay.json does not exist yet. Built by scripts/build-ci-fixture.py; --check verifies the committed fixture without rebuilding it.
